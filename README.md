# Logging & Monitoring Service

A centralized logging and monitoring backend built with the MERN ecosystem. It provides REST APIs for collecting structured application logs, searching and filtering log events, viewing log statistics, and monitoring service health and system metrics.

## Overview

The Logging & Monitoring Service helps developers collect and analyze logs generated by their applications through a centralized API.

Applications can submit structured log events containing severity levels, timestamps, service names, request identifiers, and additional metadata. The service stores these events in MongoDB and provides endpoints for querying logs and retrieving aggregate statistics.

It also exposes health-check and runtime-metrics endpoints to support basic operational monitoring.

This repository contains the backend component of a MERN-based application. A React dashboard can be developed separately and connected to these APIs.

## Features

- **Centralized logging:** Collect logs from multiple applications and services.
- **Structured log storage:** Store timestamps, severity levels, service names, environments, and metadata.
- **Bulk ingestion:** Submit up to 500 log events in a single request.
- **Log filtering:** Filter logs by severity, service, environment, date range, and message text.
- **Pagination:** Retrieve log records in manageable pages.
- **Log statistics:** View total log counts grouped by severity.
- **Error tracking:** Retrieve recent error and fatal log events.
- **Health monitoring:** Check API availability and MongoDB connectivity.
- **Runtime metrics:** Inspect process uptime, memory usage, CPU count, and host memory information.
- **API-key authentication:** Protect log-ingestion endpoints.
- **Rate limiting:** Limit excessive incoming requests.
- **Security headers:** Use Helmet to configure HTTP security headers.
- **Docker support:** Run the API and MongoDB using Docker Compose.

## Prerequisites

Make sure the following tools are installed:

- [Node.js](https://nodejs.org/) 20 or later
- [npm](https://www.npmjs.com/)
- [MongoDB](https://www.mongodb.com/) 7 or later, either locally or through MongoDB Atlas

## Installation and Setup

### 1. Clone the repository

```bash
git clone https://github.com/YOUR_USERNAME/logging-monitoring-mern.git
cd logging-monitoring
```

Replace `YOUR_USERNAME` with your GitHub username.

If you downloaded the ZIP archive instead, extract it and open the extracted directory in your terminal.

### 2. Install dependencies

```bash
npm install
```

### 3. Configure environment variables

Copy the example environment file.

On Windows Command Prompt:

```cmd
copy .env.example .env
```

On macOS or Linux:

```bash
cp .env.example .env
```

Open `.env` and configure the required values.

### 4. Configure MongoDB

For a local MongoDB installation, use:

```env
MONGODB_URI=mongodb://127.0.0.1:27017/logging_monitoring
```

For MongoDB Atlas, use your database connection string and keep credentials out of source control.

### 5. Start the development server

```bash
npm run dev
```

To start the application without Nodemon:

```bash
npm start
```

The API will be available at:

```text
http://localhost:5000
```

API reference:

```text
http://localhost:5000/api/docs
```

## Environment Variables

| Variable | Description | Example |
|---|---|---|
| `NODE_ENV` | Application environment | `development` |
| `PORT` | Server port | `5000` |
| `MONGODB_URI` | MongoDB connection string | `mongodb://127.0.0.1:27017/logging_monitoring` |
| `INGEST_API_KEY` | Secret required for log ingestion | Use a strong random secret |
| `CORS_ORIGIN` | Allowed frontend origins | `http://localhost:5173` |
| `LOG_RETENTION_DAYS` | Intended log retention setting | `30` |

**Important:** `LOG_RETENTION_DAYS` is currently a configuration placeholder. Automatic log deletion and retention enforcement have not been implemented.

Generate a strong API key and never commit your `.env` file to GitHub.

## Running with Docker

Docker Compose starts the API and MongoDB together.

### 1. Configure the ingestion key

Set the `INGEST_API_KEY` environment variable to a strong secret before starting the containers.

### 2. Build and start

```bash
docker compose up --build
```

### 3. Stop the containers

```bash
docker compose down
```

To stop the containers and remove the MongoDB data volume as well:

```bash
docker compose down -v
```

**Warning:** The last command deletes the Docker-managed MongoDB data volume. Do not use it if you need to preserve your database.

The API is available at `http://localhost:5000`.

## API Documentation

All endpoints return JSON responses.

### 1. Health Check

**Endpoint:** `GET /api/health`

Checks the application's runtime status and MongoDB connectivity.

Example:

```bash
curl http://localhost:5000/api/health
```

A healthy response includes:

```json
{
  "status": "ok",
  "timestamp": "2026-10-19T07:30:00.000Z",
  "uptimeSeconds": 120,
  "checks": {
    "database": "connected"
  }
}
```

The timestamp and uptime values depend on the running instance.

### 2. Runtime Metrics

**Endpoint:** `GET /api/metrics`

Returns basic process and host metrics, including:

- Process uptime
- Process memory usage
- CPU count
- Host load averages
- Total and available host memory

Example:

```bash
curl http://localhost:5000/api/metrics
```

These are runtime snapshots, not a full Prometheus-compatible metrics exporter.

### 3. Ingest a Single Log

**Endpoint:** `POST /api/logs`

**Authentication:** Required through the `x-api-key` header.

Example request:

```json
{
  "timestamp": "2026-10-19T07:30:00.000Z",
  "level": "error",
  "message": "Payment provider timed out",
  "service": "checkout-api",
  "environment": "production",
  "requestId": "req-123",
  "traceId": "trace-456",
  "metadata": {
    "orderId": "order-42",
    "durationMs": 1200
  }
}
```

Example cURL:

```bash
curl -X POST http://localhost:5000/api/logs \
  -H "Content-Type: application/json" \
  -H "x-api-key: YOUR_INGEST_API_KEY" \
  -d '{"level":"error","message":"Payment provider timed out","service":"checkout-api","environment":"production"}'
```

The `timestamp` field is optional and defaults to the current time.

Supported severity levels:

- `debug`
- `info`
- `warn`
- `error`
- `fatal`

The `message` and `service` fields are required.

### 4. Bulk Log Ingestion

**Endpoint:** `POST /api/logs/bulk`

**Authentication:** Required through the `x-api-key` header.

Example request:

```json
{
  "logs": [
    {
      "level": "info",
      "message": "Worker started",
      "service": "background-worker"
    },
    {
      "level": "warn",
      "message": "Retrying failed request",
      "service": "background-worker"
    }
  ]
}
```

Example cURL:

```bash
curl -X POST http://localhost:5000/api/logs/bulk \
  -H "Content-Type: application/json" \
  -H "x-api-key: YOUR_INGEST_API_KEY" \
  -d '{"logs":[{"level":"info","message":"Worker started","service":"background-worker"},{"level":"warn","message":"Retrying request","service":"background-worker"}]}'
```

A successful request returns the number of inserted records. Each request can contain up to 500 log events.

### 5. Query Logs

**Endpoint:** `GET /api/logs`

Retrieve logs with optional filtering and pagination.

Supported query parameters:

| Parameter | Description |
|---|---|
| `level` | Filter by severity |
| `service` | Filter by exact service name |
| `environment` | Filter by environment |
| `search` | Search message text |
| `from` | Start timestamp |
| `to` | End timestamp |
| `page` | Page number, starting at 1 |
| `limit` | Records per page, from 1 to 100 |

Example:

```bash
curl "http://localhost:5000/api/logs?level=error&service=checkout-api&page=1&limit=25"
```

Example date-range query:

```text
/api/logs?from=2026-10-18T00:00:00Z&to=2026-10-19T00:00:00Z
```

Example response structure:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 25,
    "total": 0,
    "pages": 0
  }
}
```

The `data` array contains the matching log documents. The example above illustrates the response structure with no matching records.

### 6. Log Statistics

**Endpoint:** `GET /api/logs/stats`

Returns the total number of logs in the selected time window, counts grouped by severity, and up to five recent error or fatal events.

Example:

```bash
curl http://localhost:5000/api/logs/stats
```

By default, statistics cover the last 24 hours.

You can optionally specify a time range and service:

```text
/api/logs/stats?from=2026-10-18T00:00:00Z&to=2026-10-19T00:00:00Z&service=checkout-api
```

### 7. API Reference

**Endpoint:** `GET /api/docs`

Returns a JSON document describing the available endpoints and query parameters.

## Security Considerations

- Protect ingestion endpoints with a strong, randomly generated API key.
- Do not expose the MongoDB port publicly in production.
- Use HTTPS for deployments.
- Restrict CORS to trusted frontend origins.
- Add authentication and role-based authorization to log-query and statistics endpoints before exposing them publicly.
- Never log passwords, access tokens, API secrets, or payment-card information.
- Consider redacting sensitive fields from log metadata.
- Configure appropriate retention, backups, and archival policies.
- Rotate API keys regularly and consider separate keys for different services.
- Review rate limits and request-size limits based on your deployment requirements.

The current API-key mechanism protects log ingestion only; the query and monitoring endpoints should not be treated as authenticated administrative endpoints.
